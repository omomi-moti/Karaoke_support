## 0001. 技術判断を ADR としてこのファイルに残す

- 2026-10-14 ／ 承認
- 背景：判断の理由を「技術的な工夫」として 1 つの文章にまとめていたため、判断が変わると上書きするしかなく、何から何に変えたかの経緯が残らなかった

### 比較した案
- A. 今までどおり「工夫と解決策」の文章を更新していく
- B. `docs/adr/` に 1 件 1 ファイルで ADR を置く
- C. このファイル 1 つに ADR を番号順に足していく

### トレードオフ
- A は書くのが楽だが、変更の経緯が消える
- B は件数が増えても探しやすく、複数人で同時に足しても衝突しにくいが、個人開発でこの規模だとファイルが散らばるだけ
- C は全体を上から読めて管理が楽。件数が増えると長くなる

### 選んだ理由
- C。個人開発で判断は当面 10〜20 件程度なので、1 ファイルで十分管理できる
- 一般的な ADR より軽くし、次の項目だけ書く
  - 日付とステータス（提案 ／ 承認 ／ 置き換え済み（→ 番号））
  - 背景（何を決めたか。1〜2 行）
  - 比較した案・トレードオフ・選んだ理由
  - 見直す条件（どうなったら見直すか）
  - 関連（Issue・PR・ドキュメント。あれば）
- 承認した項目の本文は書き換えない。判断を変えるときは新しい番号を足し、古い項目のステータスを「置き換え済み（→ 番号）」にする
- 憲法（[constitution.md](../.specify/memory/constitution.md)）が上位。ADR は憲法の範囲内での判断を書く
- 0002〜0010 は、以前「技術的な工夫と解決策」に書いていた内容を移したもの。日付は元の文章をこのファイルに書いた日

### 見直す条件
- 項目が 30 件を超えたら、または開発者が増えたら、`docs/adr/` に 1 件ずつのファイルへ分ける

## 0002. Spotify のメタデータは永続化せず、曲は ID とユーザー入力だけ持つ

- 2026-07-28 ／ 承認
- 背景：Spotify API の規約で、曲名・アーティスト名・アートワークなどの永続保存が禁止されている（憲法 I）。一方で、Spotify 未連携でも記録と振り返りはできるようにしたい

### 比較した案
- A. 取得したメタデータを SwiftData や UserDefaults に保存する
- B. `Track` には `spotifyTrackId` とユーザーが入力した曲名（`userEnteredName`）だけを持ち、表示用のメタデータは V2 でインメモリの TTL キャッシュ（24h）から取る

### トレードオフ
- A は実装が簡単でオフラインでも曲名を出せるが、規約違反になる
- B は規約を守れるが、Spotify 由来の曲はオンラインで取得するまで曲名を出せない

### 選んだ理由
- B。規約違反は選べない。V1 は `userEnteredName`（ユーザー生成データなので永続化してよい）で曲名を出し、Spotify なしでも体験が完結するようにした
- `Track` の初期化子を Spotify 用（`spotifyTrackId` 必須）と手入力用（`userEnteredName` 必須）に分け、`private init` で代入を一か所にまとめた。Spotify 連携を足すときに型の保証を壊さないため
- Spotify 由来で `Track` を作るときは `userEnteredName` を保存しない（`SwiftDataTrackRepository.getOrCreate`）

### 見直す条件
- Spotify の規約が変わったとき

関連：[constitution.md](../.specify/memory/constitution.md)（I. Spotify API 規約準拠）

## 0003. Repository は Protocol で定義し、`@Environment` で注入する

- 2026-07-28 ／ 承認
- 背景：ViewModel から SwiftData を直接触ると、テストで DB を差し替えられない。依存の渡し方を決める必要があった

### 比較した案
- A. ViewModel の中で具体的な Repository を作る、またはシングルトンを使う
- B. DI ライブラリを使う
- C. Repository を Domain の Protocol で定義し、App 起点で具体実装を作って `@Environment` で渡し、View が ViewModel の `init` に渡す

### トレードオフ
- A は簡単だが、テストで差し替えられない
- B は配線が楽になるが、外部依存が増える（憲法で DI ライブラリは使わない方針）
- C は EnvironmentKey を Repository ごとに書く手間がある

### 選んだ理由
- C。外部依存なしで差し替えられる。Repository テストは in-memory の `ModelContainer` で実際の SwiftData を使い、ViewModel テストはモックの Repository を `init` に渡して検証できている
- EnvironmentKey とプレビュー用のモックは App 層に置き、Data 層を SwiftUI に依存させない

### 見直す条件
- 依存が増えて EnvironmentKey の配線が負担になったとき

## 0004. 非同期の古い結果は世代番号で捨てる

- 2026-07-28 ／ 承認
- 背景：履歴でフィルターの変更や削除が読み込みの完了と重なると、古い読み込み結果が新しい一覧を上書きする

### 比較した案
- A. 新しい読み込みを始めるときに古い `Task` を `cancel()` するだけにする
- B. 読み込みのたびに世代番号（`loadGeneration`）を進め、完了時に自分の世代が最新のときだけ結果を反映する

### トレードオフ
- A はコードが少ないが、キャンセルは非同期に伝わるので、キャンセルが届く前に完了した古い読み込みが一覧を書き換えてしまう
- B は確実に防げる。コストは `Int` の加算と比較だけだが、反映する箇所すべてで世代を確認する必要がある

### 選んだ理由
- B。A では競合を完全に防げない。`loadInitial`・`loadNextPageIfNeeded`・`deleteSession` で同じ仕組みを使える
- 読み込みが 1 本しかなく、持ち主が `.task` で決まっている画面（曲詳細）は、世代番号を使わず `Task.checkCancellation()` で古い結果を捨てる（I-019）

### 見直す条件
- 読み込みが 1 本の Task に集約でき、キャンセルだけで古い結果を確実に捨てられる構造になったとき

## 0005. 履歴は値型のスナップショットで持つ

- 2026-07-28 ／ 承認
- 背景：一覧の行に SwiftData の `SingingSession` を直接渡すと、削除後に SwiftUI が古い参照を描画して fault で落ちることがある

### 比較した案
- A. `SingingSession` をそのまま ViewModel に持ち、一覧に渡す
- B. 取得した直後に値型（`HistorySessionRowDisplayItem`）に写して持つ

### トレードオフ
- A は写す手間がないが、削除のタイミングで落ちうる。楽観的な更新もしにくい
- B は写すコードが要るが、削除後も安全に描画できる

### 選んだ理由
- B。落ちないことを優先した。あわせて次のことができる
  - 削除は先にスナップショットから消し、DB の削除に失敗したら戻す（楽観的な更新）
  - 並べ替えや絞り込みをメモリ上で完結でき、再取得が要らない
  - 一覧で持つのは最大 500 件にして、記録が多い人でもメモリを抑える
- 曲詳細も同じ理由で `TrackScoreTrendPoint`（値型）に写している

### 見直す条件
- SwiftData の削除と SwiftUI の描画のずれで落ちる問題が解消されたとき

## 0006. 保存の冪等性を UI 層とデータ層の両方で守る

- 2026-07-28 ／ 承認
- 背景：カラオケボックス（地下など）の不安定な通信を前提に、保存ボタンの連打や再試行で同じ記録が二重に保存されないようにする

### 比較した案
- A. UI 層だけで防ぐ（保存中はボタンを押せなくする）
- B. データ層だけで防ぐ（同じ ID なら保存しない）
- C. 両方で防ぐ

### トレードオフ
- A は、タップしてからボタンが押せなくなるまでの間に 2 回目のタップが入ると防げない
- B は確実だが、保存中かどうかが画面から分からない
- C は二重に実装する手間がある

### 選んだ理由
- C。UI 層：保存ボタンをすぐ押せなくし、ProgressView と操作のブロックを出す（`isSaving`）。データ層：クライアントで作った UUID を冪等キーにし、`exists(uuid:)` で既にあれば insert と `singCount` の加算をせずに成功扱いにする
- 保存に失敗して再試行するときは同じ UUID を使う。編集は別の入口（`updateRecordingSession`）にして、冪等の判定で編集内容が無視されないようにしている

### 見直す条件
- サーバー同期を入れて、冪等性をサーバー側で保証するようになったとき

関連：I-010、I-011（[archive/v1_issues.md](archive/v1_issues.md)）

## 0007. enum を含む `#Predicate` を使わず、メモリで絞り込む

- 2026-07-28 ／ 承認（見直し候補）
- 背景：`#Predicate<SingingSession> { $0.intent == .shout }` はコンパイルが通るが、iOS 17.0〜17.2 の実機で実行時エラーになるケースがあった

### 比較した案
- A. enum を `#Predicate` でそのまま比較する
- B. RawValue（String）の比較に書き換える
- C. 直近の一定件数を `fetchAll` で取り、メモリ上で `filter` する

### トレードオフ
- A は iOS 17.0〜17.2 で落ちる
- B は `#Predicate` の型推論とぶつかって安定しなかった
- C は確実に動くが、DB で絞り込めないので、直近の件数より前の記録は Intent で絞り込んでも出てこない

### 選んだ理由
- C。落ちないことを優先した。同じ Intent でページを足すときは `intentFilterCache` で再取得を抑えている
- 曲ごとの記録の取得（`fetchSessions(trackId:)`）も、リレーションを使った述語を避けて同じ方針にしている

### 見直す条件
- 最低対応 OS が iOS 17.3 以降になったとき
  - **2026-09-23 に最低対応 OS を iOS 26 に上げたので、この条件は満たしている。** DB 側での絞り込みに戻すか、iOS 26 で `#Predicate` が安定して動くかを確認してから新しい ADR で決める

## 0008. 歌唱記録は 1 枚のシートにまとめ、`RootView` に 1 つだけ置く

- 2026-07-28 ／ 承認
- 背景：仕様では Intent 選択と歌唱記録の入力が別画面（S-004 ／ S-005）だった。また、記録画面を push で出すと、保存後にルートへ戻るとき一覧が一瞬見えるちらつきがあり、iOS 17.0 では `NavigationStack` と `.sheet` を同じ View で使うとシートを閉じた後にナビゲーションが壊れることがあった

### 比較した案
- A. 仕様どおり別画面にし、`NavigationStack` の push で順に進む
- B. 1 枚のシートにまとめ、各タブの中に `.sheet` を置く
- C. 1 枚のシートにまとめ、`RootView`（`TabView`）に 1 つだけ置き、どのタブからも同じシートを開く

### トレードオフ
- A は画面ごとの責務が明確だが、入力の途中で画面が切り替わり、保存後のちらつきとナビゲーションの不具合がある
- B はタブごとに完結するが、`NavigationStack` と `.sheet` が同じ View に並ぶ
- C は `RootView` にシートの状態が集まるので、保存後に履歴を読み込み直す仕組み（`historyReloadTick`）が別に要る

### 選んだ理由
- C。曲名・点数・気分・メモを 1 枚で途切れずに入力でき、保存後はシートを閉じて `selectedTab = .history` にするだけで遷移が終わる。各タブの `NavigationStack` はルートだけにして、`.sheet` と同じ View に並べない

### 見直す条件
- 記録の入力が 1 枚に収まらなくなったとき（写真の読み取り結果の確認など、段階的な入力が必要になったとき）
- iOS 17 の不具合は最低対応 OS を iOS 26 に上げたので前提から外れたが、ちらつきの回避と「どのタブからも同じシート」の利点は残るので、現時点では維持する

関連：[v1_navigation_songs_recording.md](v1_navigation_songs_recording.md)

## 0009. 曲名の候補は一致した場所で段を分けて並べる

- 2026-09-29 ／ 承認
- 背景：記録シートの曲名入力で、歌ったことがある曲を「もしかして」として出す。部分一致で探して歌唱回数順に並べるだけだと、「a」と打ったときに途中に a を含むだけの曲が上に来る

### 比較した案
- A. 部分一致で探し、歌唱回数順に並べる
- B. 一致した場所で段を分け（前方一致 > 単語の先頭一致 > 部分一致）、同じ段の中を歌唱回数順に並べる

### トレードオフ
- A は単純だが、打った文字で始まる曲が下に埋もれる
- B は並べ方のルールが増え、単語の区切り（アポストロフィなど）の扱いを決める必要がある

### 選んだ理由
- B。打った文字で始まる曲が上に来るほうが、探している曲に早くたどり着ける
- DB での絞り込み（`searchLocal` の部分一致）と並べ方を分け、並べ方は Domain 層の純粋な関数（`TrackSuggestionRanker`）にしてテストしやすくした
- 同じ曲かどうかの判定（完全一致）と、候補の並べ方を混ぜない

### 見直す条件
- 表記ゆれの吸収（#94〜#96）を入れて、一致の判定そのものが変わるとき

関連：[design/track_matching.md](design/track_matching.md)

- B. `v1_issues.md`・`issues.md`・`issues_with_tasks.md` を削除する

- CLAUDE.md からの読み込み（`@docs/v1_issues.md`）を外し、毎回の会話で古い内容を読ませない

## 0011. 手入力の曲は曲名＋歌手名で区別し、新しい曲では歌手名を必須にする

- 2026-10-14 ／ 提案
- 背景：手入力の曲は曲名（`userEnteredName`）だけで同じ曲かを判定しているため、別のアーティストの同名曲（「Lemon」「糸」など）が 1 曲として集計される（#97）

### 比較した案
- A. 今のまま曲名だけで区別する
- B. 歌手名を足し、入力は任意にする
- C. 歌手名を足し、新しく曲を作るときは必須にする（既存の曲を候補から選んだときは自動で入る）

### トレードオフ
- A は入力が楽だが、同名曲が混ざる
- B は入力の手間は少ないが、「a / A さん」「a / B さん」「a / 歌手名なし」の 3 つができ、歌手名なしの「a」がどちらの曲か判断できない
- C は初めて歌う曲で入力が 1 つ増える。既存のデータは歌手名がないので、データの型は任意（`String?`）のままにし、必須チェックは記録シートで行う必要がある

### 選んだ理由
- C。B では同名曲が混ざる問題が「歌手名なし」の形で残る。歌手名が必要なのは初めて歌う曲だけで、2 回目以降は候補を選べば自動で入る。歌手名はカラオケの画面に出ているので、写真の読み取り（段階 3）で入力の手間も減らせる
- 歌手名なしの既存の曲と同じ曲名を歌手名付きで記録したときは、既存の曲に歌手名を補って同じ曲として扱う
- Spotify 由来の曲は Spotify の曲 ID で区別するので、歌手名は不要（歌手名も永続化しない。0002）

### 見直す条件
