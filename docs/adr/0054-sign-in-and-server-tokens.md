# 0054. サインインは Apple だけにし、サーバーのトークンはハッシュにして持つ

- 2026-11-10 ／ 承認
- 背景：記録をバックアップする（C1）ために、Sign in with Apple でサーバーのアカウントを作る（ADR 0049・0053）。サーバーのトークンの持ち方、Apple のトークンの確かめ方、端末での置き場所、失敗したときの返し方を決める

## 比較した案

1. ログインの方法
- A. Sign in with Apple だけ
- B. Google のログインだけ
- C. Apple と Google の両方
- D. 最初に出す復元コードを、新しい端末で入力する
- E. メールアドレスとパスワード

2. Apple のトークンの確かめ方
- A. `golang-jwt/jwt` で確かめ、Apple の公開鍵の取得とキャッシュは `MicahParks/keyfunc` に任せる
- B. `coreos/go-oidc`（OpenID Connect の ID トークンを確かめる専用のライブラリ）
- C. `lestrrat-go/jwx`（JWT まわりを全部まとめたライブラリ）
- D. `go-jose` で確かめ、公開鍵の取得とキャッシュは自分で書く
- E. 標準ライブラリだけで自分で書く

3. nonce を誰が作るか
- A. iOS が作る。サーバーは発行時刻が古すぎないかも確かめる
- B. サーバーが作り、1 回だけ使える値として覚えておく

4. サーバーのトークンの形
- A. `crypto/rand` で作った値を返し、DB にはその SHA-256 のハッシュだけを置く
- B. サーバーが署名した JWT を返し、DB には何も置かない
- C. 作った値をそのまま DB に置く

5. サーバーのトークンの期限
- A. 90 日で固定
- B. 使うたびに延ばす
- C. 使うたびに延ばすが、最長 1 年まで

6. 期限切れの行の掃除
- A. サインインのときに、その人の期限切れの行を消す
- B. 定期的に動く仕組み（Cloud Scheduler）で消す
- C. 消さない

7. 端末でのトークンの置き場所
- A. Keychain に `AfterFirstUnlockThisDeviceOnly` で置く
- B. Keychain に `WhenUnlockedThisDeviceOnly` で置き、ロックが解けている間に読んでメモリに持つ

8. 失敗したときの返し方
- A. 理由に関係なく 401 を返す
- B. 利用者の側の失敗（トークンが偽物・期限切れ）は 401、サーバーの側の失敗（Apple や DB に届かない）は 5xx を返す。返事の本文は決まった形の JSON にする

## トレードオフ

- 1-A は iPhone なら Face ID だけで済み、パスワードもメールアドレスも持たない。Android や Web では Web の画面を通すので少し回りくどい。1-B は Android や Web で自然だが、App Store の審査の決まり 4.8 で、外部のログインには Apple のようなプライバシーを守れるログインを並べることが求められ、Google だけでは通らない見込み（4.8 は要約で読み、原文では確かめていない）。Google の SDK という外部の依存も入る。1-C は決まりに合うが、同じ人が 2 つのアカウントになる問題が最初から起きる。1-D は Apple に関わる作業がなくなるが、端末をなくしたときにコードも持っていなければ戻せず、バックアップの意味が薄れる。1-E はパスワードの保管・再設定のメール・メールアドレスの保管が要り、いちばん重い。ADR 0049 の「持たない情報は漏れない」にも反する
- 2-A は、`RS256` だけを受け付ける・発行者・宛先・期限・発行時刻・時計のずれの許容を、どれも設定で指定できる。知らない鍵の ID での取り直しに回数の制限を付けられ、通信のタイムアウトも指定できる。依存が 4 つ増え（golang-jwt・keyfunc・jwkset・`x/time`）、鍵を定期的に取り直す処理が裏で動く。2-B は目的にいちばん近いが、取り直しの回数の制限と時計のずれの許容の設定が文書になく、発行時刻を確かめるかも文書から分からない。2-C は全部そろうが大きく、v3 にはもう v4 が出ている。2-D は依存が少ないが、鍵の取得とキャッシュを自分で書くことになる。2-E は依存がなく中身を説明しやすいが、1〜2 時間増え、書き間違いの危険が残る
- 3-A は作りが単純で、iPhone のアプリでは一般的なやり方。Apple のトークンと元の nonce の両方を盗まれると、発行時刻の許す間は使い回される。3-B は使い回しを確実に止められるが、nonce を配る API と覚えておく場所が増える
- 4-A はログアウトで行を消せばすぐ使えなくなる。DB の中身が漏れても、ハッシュからは元の値に戻せず、そのままでは使えない。トークンは 32 バイトの乱数で総当たりできないので、人が決めるパスワード向けの bcrypt は要らず、SHA-256 で足りる。4-B は DB を引かずに済むが、期限まで取り消せない。4-C は作りが最も単純だが、DB が漏れるとそのまま使われる
- 5-A は単純だが、90 日で自動のバックアップが止まり、サインインし直すまで送られない。5-B は止まらないが、盗まれたトークンもずっと使える。5-C はその間だが、作りが増える
- 6-A は仕組みを足さずに済む。サインインしない人の行は残る。6-B は確実だが、GCP の設定が増える。6-C は行がたまり続ける
- 7-A は電源を入れて一度ロックを解いた後なら、ロック中も読める。アプリを閉じてすぐロックしても、自動のバックアップ（ADR 0053 の 5-B）が送れる。端末の外には出ない。7-B は守りがわずかに固いが、メモリの値と Keychain の値がずれる場合を考える必要がある
- 8-A は単純だが、Apple が落ちたときにも iPhone が「サインインし直して」と出してしまう。8-B は iPhone が「サインインし直す」と「時間をおいてもう一度」を出し分けられる

## 選んだ理由

- 1 は A。Google だけでは審査に通らない見込みで、Apple を外せない。Apple だけで作っておけば、Android や Web を始めるときにほかのログインを足せる。サーバーのトークンとバックアップは Apple に依存しないので、足すのは入口だけで済む
- 2 は A。条件に全部、設定で答えられるのは A だけだった。自分で書く時間を、サーバーの残りの部分に回す。ライブラリの設定の誤りは、偽のトークンで失敗する場合を全部確かめるテストで拾う
- 3 は A。iPhone のアプリで一般的なやり方で、発行時刻を確かめれば使い回せる時間を短くできる
- 4 は A。ログアウトで本当に使えなくしたい。DB が漏れても、トークンとしては使えないようにする
- 5 は A。外部テストの期間は 90 日より短い。切れたら iPhone でサインインし直しを促す
- 6 は A。今の大きさなら、仕組みを足さずに済むほうがよい
- 7 は A。自動のバックアップがロック中に読めないと、気づかないうちに送れなくなる
- 8 は B。サーバーの側の失敗で、利用者にサインインし直させない

## 決めたこと

- Apple のトークンは、`RS256` だけ・発行者（`https://appleid.apple.com`）・宛先（バンドル ID。環境変数で渡す）・期限・発行時刻・nonce を確かめる。発行時刻が 10 分より前のトークンははじく。golang-jwt の `WithIssuedAt` は未来の発行時刻をはじくための設定で、古さは見ない見込みなので、古さは自分で比べる（#152 で確かめる）。時計のずれは 1 分まで許す
- Apple の公開鍵は keyfunc でキャッシュし、知らない鍵の ID での取り直しは数分に 1 回までにする。Apple への通信は 5 秒で諦める。起動のときに Apple に届かなくても、サーバーは起動できるようにする
- サーバーのトークンは `crypto/rand` の 32 バイトから作り、`klog_` で始める。間違えて貼ったときに、秘密の検出で見つけやすくするため
- `users` の `apple_user_id` を使うのは、ユーザーを探す・作る処理だけにする。Apple の検証から先には `sub` だけを渡す
- エラーの返事は `{"error": "..."}` の形にし、`error` には決まった短い英語の値（`unauthorized` など）を入れる。詳しい理由はログにだけ出す
- 依存を足すときは最新の版を確かめ、karaoke-review の `govulncheck` で脆弱性を見る

## 見直す条件

- Android や Web を始めるとき（`users` から Apple の ID を、ログインの方法ごとの表に分け、ほかのログインを足す）
- App Store にアカウントを出す準備を始めるとき（5 を B か C にするか、短い期限と更新用のトークンに分けるかを考える。4.8 を原文で確かめる）
- トークンや nonce の使い回しが問題になったとき（3 を B にする）
- golang-jwt か keyfunc の手入れが止まったとき、または直らない脆弱性が出たとき（2 を見直す）
