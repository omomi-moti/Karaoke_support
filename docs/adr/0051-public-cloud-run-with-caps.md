# 0051. Cloud Run は公開し、台数と支出に上限を付ける

- 2026-11-04 ／ 承認
- 背景：ADR 0048 で、サーバーを Cloud Run に置くと決めた。iPhone のアプリから呼ぶには、誰でもリクエストを送れるようにする必要がある。GCP は請求に上限がなく、予算のアラートは知らせるだけで止めない。staging に初めてデプロイする前に、呼べる人・お金の止め方・秘密の置き場所・回数の絞り方・デプロイのやり方を決める

## 比較した案

1. 呼べる人
- A. 誰でも（`--allow-unauthenticated`）。データの API はサーバーのトークンで守る
- B. Google の IAM で権限を持つ人だけ（初期設定）
- C. API Gateway を前に置き、鍵を持つ人だけ

2. お金の止め方
- A. 予算のアラートだけ
- B. A に加えて、インスタンスの上限を 1 にする
- C. B に加えて、Cloud Run の支出の上限つき予算（Spend cap budget）を入れる
- D. B に加えて、予算から Pub/Sub と関数を通して、プロジェクトの請求先を外す

3. DB の URL の置き場所
- A. Cloud Run の環境変数に直接書く
- B. Secret Manager に置き、専用のサービスアカウントにそれを読む権限だけを付ける

4. 回数の絞り方（レート制限）
- A. Cloud Armor
- B. Go のミドルウェアで、IP ごとの回数をメモリで数える
- C. 入れない

5. デプロイのやり方
- A. `gcloud run deploy --source` で、Cloud Build にイメージを作らせる
- B. 手元の Docker で amd64 のイメージを作り、Artifact Registry に送ってからデプロイする

## トレードオフ

- 1-A はどこからでも届く。URL はアプリから取り出せるので、守りは URL を隠すことではなく、サーバーのトークンの確認になる。今、外に出ているのは `/health` だけ
- 1-B は Google が入口で弾くので最も固いが、アプリの利用者は GCP のアカウントを持たないので届かない
- 1-C は入口で鍵を確かめられるが、アプリに埋めた鍵は取り出せるので守りにならず、サービスが 1 つ増える
- 2-A は手間がないが、知らせるだけで止めない。費用は遅れて集計される
- 2-B は CPU とメモリの時間を抑えるが、リクエストの件数の課金は抑えない
- 2-C は、Cloud Run の月の費用が上限に届くと、新しいリクエストを止める。翌月 1 日に戻り、手で外すこともできる。画面の設定だけで、新しい技術は増えない。集計の遅れの分は上限を超えて請求される。1 つのプロジェクトの 1 つのサービスごとで、Cloud Run 以外（イメージの置き場・Secret Manager）は止めない
- 2-D はプロジェクトの全部を止められるが、関数に請求先の管理者の権限が要り、Google の文書はリソースが戻らずに消えることがあると警告している。Pub/Sub と関数が増える
- 3-A は手軽だが、Cloud Run の設定を見られる人に URL が見える
- 3-B は URL を読めるのが Cloud Run のサービスアカウントだけになる。初期設定のサービスアカウントは権限が広いので、専用のものを作る
- 4-A はロードバランサーが要り、月に数千円かかる
- 4-B はインスタンスが 1 台なら正しく数えられ、0 円。台数を増やすと台ごとにばらける
- 4-C は手間がないが、ログインの API を叩き続けられる
- 5-A はコマンドが 1 つで済むが、Cloud Build と、ソースを置くストレージが増える。ビルドを GCP 側のアカウントで動かすので、その権限も考えることになる
- 5-B はコマンドが 3 つ（作る・送る・デプロイ）になり、ARM の Mac では `--platform linux/amd64` を付けて作るので時間がかかる。使うサービスは増えず、手元で `docker run` して確かめたイメージがそのまま動く

料金と地域は 2026-11-04 に確かめた。東京（`asia-northeast1`）は Cloud Run の料金の区分が Tier 1（Cloud Run のロケーションの文書）。支出の上限つき予算は、Google の文書で Cloud Run が対象と書かれている。段階は文書に書かれておらず、第三者の資料では 2026-10-13 に GA。Cloud Run の無料枠の量は公式の料金のページで読めなかったが、支出の上限があるので、ADR 0048 の「月 0 円を目指す」前提は崩れていない。

2026-11-04 に staging にデプロイし、`gcloud run services describe` で、インスタンスの上限が 1、呼べる人が `allUsers`、専用のサービスアカウント、Secret Manager からの `DATABASE_URL` になっていることを確かめた。温まった後の `/health` は 0.12〜0.33 秒（東京の Cloud Run からシンガポールの Neon まで）。

## 選んだ理由

- 1 は A。iPhone から呼ぶには、これしかない。データの API は、Issue 2 で作るトークンの確認で守る
- 2 は C。インスタンスは 1 でよい。使う人は自分とテスター数人で、1 台で足りる。予算のアラートはプロジェクト全体に月 500 円（実際の額で 50%・90%・100%、予測で 100%。無料トライアルのクレジットは差し引かずに数える）、Cloud Run の支出の上限は月 300 円にする。上限が効くのは Cloud Run だけなので、ほかの費用はアラートで気づく。止まってもアプリは端末だけで動く（NFR-10）
- 3 は B
- 4 は B。データの API ができ、外部テスターに配る前に入れる
- 5 は B。使うサービスと外に出るものを増やさず、手元で確かめたイメージをそのまま動かす。Dockerfile の続きとして、何が起きているかが見える。イメージのタグはコミットの ID にする

## 見直す条件

- インスタンスの上限を 2 以上にするとき（4 を数え直す。共有の置き場が要る）
- 上限で止まって困ったとき、または Cloud Run 以外の費用がアラートを超えたとき（2）
- 支出の上限つき予算の仕様が変わったとき（2 を D にするかを考える）
- デプロイを GitHub Actions で自動にするとき（5）
- 無料トライアルが終わるとき（2027 年 2 月の初め。有料のアカウントに切り替えるかを決める）
