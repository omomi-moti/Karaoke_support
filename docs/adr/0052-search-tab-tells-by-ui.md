# 0052. 検索タブは、説明の文字ではなく UI で「曲名で探す画面」だと伝える

- 2026-11-05 ／ 承認
- 背景：検索タブには分かりにくいところが 4 つあった。
  - 何で探せるのかが分からない（探せるのは記録した曲の曲名だけ）
  - 行に › があるのに、タップすると曲詳細ではなく記録シートが開く
  - 開いても検索欄にカーソルが入らない
  - 行の見た目と日付の書き方が、選曲画面と違う
  
  iOS 26 では検索欄が画面の下にあり、結果は上から並ぶ。そのため、結果が親指から遠いことも気になっていた。HIG の Search fields と照らし合わせて決めた

## 比較した案

1. 何の画面かの伝え方
- A. 説明の文字（「過去に歌った曲の曲名で探せます」などの案内や注記）を画面に足す
- B. 文字は足さず、UI で伝える。開いたらすぐ検索欄に焦点を当ててキーボードを出し、検索欄の文字は「曲名で探す」にする

2. 何も打っていない間の画面
- A. 今のまま何も出さない（真っ黒な画面）
- B. 画面の本文に自前の一覧を置き、最近歌った曲を新しい順に 5 件並べる（最初に作った形。案内の文字と、履歴の行と同じ大きさのカードを並べた）
- C. 最近歌った曲を新しい順に 5 件、iOS 標準の検索の候補（`searchSuggestions`）として、検索欄が有効な間だけ出す。検索をやめたあとの画面には、候補と同じ見た目の一覧で出す

3. 結果の並び
- A. 下から積む（検索欄に近いほうに関係の深い結果を置き、親指で押しやすくする）
- B. 上から並べる。並びは今のまま、歌った回数の多い順

4. 結果の行
- A. 最初に作った形にする。履歴の行と同じ大きさのカードに、気分のバッジと最高点も出す
- B. 小さい行にする。曲名・ハート・「N回歌った ・ 前回はX前 ・ 気分」（回数と日付は選曲画面と同じ書き方）・右端の ＋ だけを出し、点数と › は出さない

5. 打ち終わりを待つ 0.3 秒と、検索している間の表示
- A. `ProgressView` を出す
- B. 前の問い合わせの結果をそのまま残し、結果がまだ 1 件もなければ何も出さない。「該当する曲が見つかりません」は、検索が終わって 0 件と分かったときだけ出す

## トレードオフ

- 1-A は確実に伝わるが、画面に文字が増え、説明に頼った画面になる。1-B は文字を読まなくても打ち始められるが、曲名以外では探せないことは画面からは分からない
- 2-A は作りがいちばん単純だが、開いたときに何もない黒い画面になり、何を探せるかの手がかりもない
- 2-B は見た目を自由に作れて目に入りやすいが、検索欄より最近の曲が画面の主役になり、検索の画面か分かりにくくなる
- 2-C は最近の曲が検索欄の一部として出るので、「検索している最中」に見える。HIG の「打つ前に候補を出す」にも沿う。ただ、候補の見た目は iOS に任せることになり、検索をやめたあとの一覧とは別に作るので、そろえないと同じ曲が違う見た目で出る。どの案でも、選曲画面と同じ曲が重なって出ることがある
- 3-A は押しやすいが、関係の深い結果を先に（上に）出す HIG の考え方と、上から読む iOS の一覧の並び方から外れる。キーボードを閉じると結果の位置も変わる。3-B は標準どおりだが、上のほうの結果は親指から遠い。結果をスクロールしたらキーボードを閉じることで、少し和らげる
- 4-A は 1 行で分かることが多いが、1 画面に入る行が少なく、検索の結果としては大きすぎる。点数は、曲を見つけて記録を始めるのには使わない。4-B はたくさん並べられ、＋ で「この曲で記録する」と分かるが、気分はバッジではなく文字になり、目立たなくなる
- 5-A は「探している」と伝わるが、ローカルの検索はすぐ終わるので、打つたびにぐるぐるがちらつく。5-B はちらつかないが、問い合わせを変えた直後の 0.3 秒ほどは、前の問い合わせの結果が出ている

## 選んだ理由

- 1 は B。説明の文字を足すと「AI っぽい」画面になる。検索の画面であることは、文字ではなく UI で伝わるべきだと考えた
- 2 は C。真っ黒な画面よりは、打つ前に最近の曲が出るほうがよい。ただ、B で作ってみると最近の曲が前に出過ぎて、検索の画面か分かりにくくなった。C なら最近の曲が検索欄の候補として出るので、それ自体が「ここは検索の画面だ」という UI の合図になる（1 と同じ考え方）。検索をやめたあとの一覧も、同じ曲が違う見た目で出ないよう、候補の見た目にそろえた。選曲画面と重なってもかまわないので、件数は 5 件にした
- 3 は B。A は HIG に沿わない動きになるため
- 4 は B。行に点数は要らず、カードは大きすぎる。行の見た目は、検索の候補（2-C）と同じにそろえた
- 5 は B。ローカルの検索はすぐ終わるので、ぐるぐるを毎回ちらつかせるより、前の結果を残すほうが落ち着いて見える

## 見直す条件

- 曲名以外（メモ・歌手名など）でも探したいと言われたとき（別の Issue にする）
- 上のほうの結果に親指が届かず押しにくいと、実機で言われたとき（3）
- 最近の曲が選曲画面と重なって邪魔だと言われたとき（2）
- MusicKit などネットワーク越しの検索を足して、検索に時間がかかるようになったとき（5 を A にする）
