# 0034. 記録の入口は空を許す enum で持ち、空は手で付けた記録として読む

- 2026-10-25 ／ 承認
- 背景：選曲MVP の仮説「保存した直後に過去の曲を見せれば、次の 1 曲が決まる」を確かめるため、記録に入口（提案から付けたか、それ以外か）を持たせる（#120）。最初は `SingingSession` に `source: RecordSource = .manual` を足す予定だった。前のビルドで作ったデータを新しいビルドで開いて確かめると、自動の移行で足された列は前からある記録では空のままで、`source` を読むと `Could not cast value of type 'Optional<Any>' to 'RecordSource'` で落ちた。プロパティに書いた初期値は、Swift で新しく作るときにしか使われない

## 比較した案
- A. 空を許す `recordedSource: RecordSource?` に保存し、読むときは `source`（空なら `.manual`）を使う
- B. 文字列（`String`、初期値 `"manual"`）で保存し、enum に直せないときは `.manual` として読む
- C. `VersionedSchema` と移行の手順を足し、前からある記録に `manual` を書き込む

## トレードオフ
- A は前からある記録を空のまま読める。保存する項目と読む項目で名前が 2 つになり、`intent` と書き方がそろわない。空は「入口を記録し始める前の記録」として、手で付けた記録と見分けられる
- B も落ちずに読めるが、列は空のままで、読めるのは「直せないときは `.manual`」のおかげ。読める理由が見えにくい
- C は空が残らないが、起動時に元のデータを書き換える処理が入る。[0033](0033-show-error-when-store-cannot-open.md) で避けた「元のデータに手を付ける」ことになり、失敗したときの扱いも考える必要がある

## 選んだ理由
- A。前からある記録を落とさずに読めることを、移行の処理なしで満たせる。空が残ることは、入口を記録し始める前と後を見分けられる良さにもなる
- 保存する項目は `private(set)` にし、`init` は空を許さない `RecordSource` で受け取る。新しい記録には必ず `manual` か `suggestion` が入り、空になるのは前からある記録だけ
- 編集で更新しても入口は変えない。前からある記録は編集しても空のまま
- 提案のカードから開いても、曲を書き換えて保存したら `manual` にする。気分だけ変えたときは `suggestion` のまま
- 提案から記録した数は、設定画面の「テストへのご協力」の欄に「提案から記録した数 ／ 入口を記録し始めてからの記録の数」で出し、テスターにスクリーンショットを送ってもらう。入口が空の記録はどちらの数にも入れない（前からある記録を分母に入れると、割合が実際より低く見えるため）
- この欄はテスターのビルドだけで出し分けず、すべてのビルドで出す。テスターのビルドを見分ける StoreKit の `AppTransaction` は、購入の記録がないと Apple Account のサインインを求めることがあったため。今は TestFlight でしか配っていないので困らない。App Store に出す前に、この欄を消す
- 0033 には「初期値付きの項目を 1 つ足すだけなら自動の移行で済む」と書いたが、enum の項目では成り立たなかった。モデルに項目を足すときは、空を許す形で足し、前のビルドのデータを新しいビルドで開いて読めることを確かめる

## 見直す条件
- App Store に出すとき（設定画面の「テストへのご協力」の欄を消す）
- 入口で DB を絞り込む必要が出たとき（読む項目は計算なので `#Predicate` で使えない。空と `manual` の両方を条件に書く）
- 初期値で済まない項目の変更をするとき（`VersionedSchema` を入れる）
