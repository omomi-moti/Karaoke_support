# 0029. 提案に使う曲ごとの集計はキャッシュせず、保存のたびに全部の記録から作り直す

- 2026-10-24 ／ 承認
- 背景：保存直後のシート（#115）で、曲ごとの集計（最新の気分・最後に歌った日時・最高点・回数）が要る。保存のたびに全部の記録を読み直すか、集計をどこかに持っておくかを決める

## 比較した案
- A. キャッシュせず、保存のたびに全部の記録を読み、曲ごとにまとめ直す
- B. メモリ上に集計をキャッシュし、保存・編集・削除のたびに差分で直す
- C. `Track` に集計の値（最新の気分・最後に歌った日時・最高点）を保存しておく

## トレードオフ
- A は一番簡単で、必ず最新になる（編集で日時や気分を直した・記録を消した、も何もしなくても反映される）。ただし、かかる時間は記録の数に比例し、`ModelContext` を扱うのでメインスレッドで動く。記録が何千件にもなると、保存してからシートが出るまでの間が伸びる
- B は速いが、保存・編集・削除のすべての経路でキャッシュを正しく直す必要があり、直し忘れると古い集計で提案が出る。アプリを起動し直したときの作り直しも要る
- C は読むのが速いが、`Track` の項目が増えてモデルの移行が要る。`singCount` と同じように、記録と集計がずれうる経路が増える

## 選んだ理由
- A。今の記録の数（1 人で数百件くらい）なら一瞬で終わるので、ずれる心配がない方を取る。提案の正しさ（今日歌った曲を外す、最新の記録の気分で判断する）は、集計が最新であることに頼っている
- 読み込みは `TrackStatsRepositoryProtocol.fetchTrackSingingStats()` の 1 つに閉じている。遅くなったときも、呼び出し側（`AfterSaveRecommendationViewModel`）を変えずに、Repository の中身だけを B や C に替えられる

## 見直す条件
- 保存してからシートが出るまでに、待たされると感じたとき。まず Instruments で `fetchTrackSingingStats()` にかかる時間を測り、そのときの記録の数と一緒に残す
- 選曲画面（スプリント 4）で、気分を切り替えるたびに集計を読むようになったとき（呼ぶ回数が増える）
