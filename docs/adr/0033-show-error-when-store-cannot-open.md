# 0033. 保存先の DB を開けなかったときは、メモリ上の DB で起動せず、エラー画面で止める

- 2026-10-25 ／ 承認
- 背景：起動時に保存先の DB（SwiftData）を開けないと、開発中は `assertionFailure` で止まるが、リリースのビルドではメモリ上の空の DB で起動していた。テスターの端末では記録が全部消えたように見え、新しく保存した記録も次の起動で消える。本人はそれに気づけない。選曲MVP のスプリント 2（#120）で初めてモデルに項目を足すので、その前に直す

## 比較した案
- A. 今までどおり、メモリ上の空の DB で起動する
- B. `fatalError` で落とす
- C. 開けたかどうかを状態として持ち、開けなかったら「データを読み込めませんでした」の画面だけを出す。元のデータには手を付けない

## トレードオフ
- A はアプリを使い続けられるが、記録が消えたように見え、その後の記録も残らない。データを失うのに、本人には何が起きたか分からない
- B は空の DB で記録を続けてしまうことはないが、起動するたびに落ちるだけで、何が起きたかも、アプリを消してはいけないことも伝わらない
- C は画面と分岐が 1 つずつ増える。記録はできないが、データは端末に残っていると伝え、知らせてもらえる

## 選んだ理由
- C。データを失わないことと、何が起きたかを本人に伝えることを優先する。エラー画面では、アプリを削除せずに TestFlight のフィードバックから知らせてほしいと書く
- 保存先の元のデータは消さない・作り直さない。開けなかった理由は `os.Logger` でログに残し、開発中に原因を追えるようにする
- DB と Repository を作るのは `AppDependencies.make(configuration:)` の 1 か所にまとめ、App は結果（`Result<AppDependencies, any Error>`）を見て、`RootView` とエラー画面を出し分ける。作る処理を App から外したので、開けなかったときに throw することをテストで確かめられる
- UI テスト用のメモリ上の DB（`KARAOKE_UITEST_IN_MEMORY`）は今までどおり使う。こちらは作れなければ `fatalError` のまま
- エラー画面を確かめるため、デバッグのビルドでだけ使える環境変数 `KARAOKE_SIMULATE_DATA_LOAD_FAILURE=1` を足した。`#if DEBUG` の中にあるので、リリースのビルドには入らない
- 移行に版（`VersionedSchema`）は付けない。初期値付きの項目を 1 つ足すだけなら自動の移行で済む。代わりに、古いビルドのデータを新しいビルドで開いて記録が消えないことを、スプリント 2 で手で確かめる

## 見直す条件
- エラー画面が実際にテスターの端末で出たとき（原因に合わせて、移行の版や復旧の手段を考える）
- 初期値で済まない項目の変更（名前の変更・型の変更・必須の項目の追加など）をするとき（`VersionedSchema` を入れる）
