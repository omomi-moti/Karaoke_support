# 0056. Apple の公開鍵を 1 つも持っていないときだけ、サインインを 5xx にする

- 2026-11-12 ／ 承認
- 背景：ADR 0054 で、利用者の側の失敗は 401、Apple や DB に届かないなどサーバーの側の失敗は 5xx にすると決めた。ところが #152 の時点では、Apple の公開鍵を取りにいけなくてもサインインが 401 になっていた。keyfunc（jwkset）が、鍵の取り直しの失敗を「鍵が見つからない」と同じエラーで返し、偽物のトークンと見分けられないため。staging の Cloud Run は使われないとゼロまで止まり、起動のたびに Apple へ鍵を取りにいく。そのときに届かないと、そのインスタンスは鍵を持たないまま動き、どのサインインも 401 になる（#153）

## 比較した案

- A. そのリクエストの中で鍵の取り直しが失敗したら 5xx にする（keyfunc の `RefreshErrorHandlerFunc` に、リクエストの `ctx` を通して知らせる）
- B. Apple へ最後に鍵を取りにいったときに成功したかをフラグで覚え、鍵が見つからず、フラグが失敗のときに 5xx にする（自前の HTTP クライアントと `RefreshErrorHandlerFunc` でフラグを書く）
- C. 何も変えず、401 のままにする
- D. 鍵が見つからず（`jwt.ErrTokenUnverifiable`）、しかも keyfunc のキャッシュに鍵が 1 つもないときだけ 5xx にする

## トレードオフ

- A は、取り直しに失敗した後の 5 分間、回数の制限で取り直しそのものが行われず、失敗が記録されない。その間は 401 に戻る
- B は、鍵を替えた直後に Apple に届かない場面（下の③）でも 5xx にできる。代わりに、「Apple に届くか」という状態をサーバーに持ち、書く場所が 2 つになる。Apple が戻っても、次に取りにいって成功するまでフラグは失敗のまま残る
- C は、変えるものがない。代わりに、起動のときに Apple に届かないと、利用者には「もう一度お試しください」と出続け、サーバーの問題だと分からない
- D は、状態を持たず、keyfunc のキャッシュを読むだけで済む。起動のときに Apple に届かない場面（①）は 5xx にできる。代わりに、③は 401 のまま残る

B と D で結果が違うのは、次の場面だけ。

| 場面 | B | D |
|---|---|---|
| ① 起動のときに Apple に届かず、鍵を 1 つも持っていない | 5xx | 5xx |
| ③ 鍵は持っているが Apple に届かず、本物だが手元にない新しい鍵のトークン（Apple が鍵を替えた直後） | 5xx | 401 |
| ⑥ 鍵は持っているが Apple に届かず、知らない鍵の ID の偽物 | 5xx | 401 |

③が起きるのは、Apple が鍵を替えた時と、Cloud Run から Apple に届かない時が重なったときだけ。起きても、利用者に見える違いは文言（「もう一度お試しください」か「時間をおいて」か）で、記録には何も起きない。⑥は偽物なので、どちらで答えてもよい

## 選んだ理由

- D にする。B は③も正しく扱えるが、違いはまれな③の文言だけで、そのためにサーバーへ「Apple に届くか」という状態を持ち込むのは割に合わない。状態があると、読むときもテストするときも、フラグが今どちらかを考え続けることになる
- 現実に起きやすいのは、Cloud Run が起動のときに Apple に届かない①で、D はそこを状態なしで守れる
- A は、守りたい①の場面でも 5 分間だけしか効かないので選ばない

## 決めたこと

- `appleauth.Verifier.Verify` は、トークンの検証が `jwt.ErrTokenUnverifiable`（鍵を探せない）で失敗し、しかも `KeySource.HasKeys` が false のときだけ、`ErrKeysUnavailable` を返す。それ以外の失敗は今までどおり `ErrInvalidToken`（401）
- `ErrKeysUnavailable` は `ErrInvalidToken` ではないので、`account.Service` はサーバーの側の失敗として扱い、ハンドラーは 500 を返してログに出す
- `HasKeys` は keyfunc のキャッシュ（`Storage().KeyReadAll`）を読むだけで、Apple には問い合わせない
- 手元の鍵で確かめられるトークンは、Apple に届かなくても今までどおり確かめる（期限切れ・nonce 違いなどは 401）
- #153 の受け入れ条件「確かめられないときは 5xx を返す」は、「鍵を 1 つも持っていないときは 5xx を返す」の意味で満たす。③は 401 のまま残す

## 見直す条件

- ③が実際に起き、利用者が困ったとき（そのときは B を考え直す）
- Cloud Run のインスタンスを常に 1 つ起こしておくようにし、起動のときの取りにいく回数がほとんどなくなったとき
- keyfunc（jwkset）が、取り直しの失敗を「鍵が見つからない」と見分けられるエラーで返すようになったとき
