# 0053. 外部テスターには Beta のビルドで配り、バックアップは自動で取る

- 2026-11-06 ／ 承認
- 背景：ADR 0049 の 6 で、アカウントとバックアップはデバッグのビルドでだけ出すと決めた。2026-11-02 に、C1 を 11 月末に TestFlight の外部テスターへ配り、MusicKit も M2 まで入れる方向に広げた。TestFlight のビルドはリリースのビルドなので、出し方・配る前に済ませること・アプリの中の表示を決め直す。あわせて、毎回ボタンで送る形（FR-3）だと押し忘れでバックアップが役に立たないので、送るきっかけも決め直す

## 比較した案

1. 11 月末までに入れるもの
- A. C1 だけ。MusicKit は後
- B. C1 を先に作り、その後に MusicKit（M1 → M2）を入れる。MusicKit が間に合わなくても、C1 ができたら配る
- C. C1 と M2 まで全部を入れてから配る

2. TestFlight のビルドへの出し方
- A. Release を写した Beta のビルドの設定を足し、`BETA` の印で出し分ける。TestFlight は Beta、App Store は Release でアーカイブする
- B. 1 つのビルドで、`AppTransaction` で TestFlight か App Store かを見分けて出し分ける
- C. バンドル ID の違う別のアプリにする

3. アカウントの削除のときの Apple のトークンの取り消し
- A. 消すときにもう一度 Sign in with Apple を出し、そのとき来た認可コードで取り消す
- B. ログインのときに Apple のトークンを受け取って DB に置き、消すときに使う
- C. 取り消さない

4. アプリの中の、データをどこに保存するかの表示
- A. ビルドで文を切り替える。Release は今の文、Debug と Beta は決まり（何を送り、何を送らないか）を書いた文
- B. Beta では、バックアップをオンにしたかでも文を切り替える

5. バックアップを送るきっかけ
- A. 毎回、設定画面のボタンで送る（今の FR-3）
- B. オンにした後は、アプリを閉じたときに自動で全件を送る。空の端末からは送らず、ほかの端末から送ったバックアップを上書きしそうなときは止めて聞く。ボタンは「今すぐ」として残す
- C. 記録ごとに変わった分を送り合う同期（C2・C3）を先に作る

## トレードオフ

- 1-A は確実に間に合うが、MusicKit が計画から消える。1-B は C1 を先に固め、MusicKit は残りの時間で進められる。1-C は 11 月末に間に合わない見込み（11/5〜11/30 に使えるのは 1 日 1.5 時間でおよそ 39 時間）
- 2-A は App Store のビルドにアカウントのコードが入らず、「記録を送らない」と言い切れる。代わりに、TestFlight に上げた Beta のビルドを間違えて App Store の審査に出さない決まりが要る。2-B はビルドが 1 種類で済むが、App Store のビルドにもコードが入り、見分けを間違えると利用者に見える。見分け方が正しく動くかは確かめていない。2-C は混ざらないが、Sign in with Apple・App Store Connect・設定を 2 つずつ持つ
- 3-A は Apple のトークンを DB に持たずに済む。消すときに Apple の画面が 1 回余分に出る。3-B は操作が 1 回で済むが、長く使える Apple のトークンを DB に持ち、守りが要る。3-C は手間がないが、外部の人に配るのに、Apple の側にアカウントのつながりが残る。3-A と 3-B はどちらも、Apple の鍵（.p8）を Secret Manager に置くことと、署名（ES256）が要る。Issue 2 が 3〜5 時間ほど増える
- 4-A はどちらのビルドでも正しく、Release の画面は変わらない。Beta の文は、まだオンにしていない人にも出る。4-B はその人の状態に合うが、状態が増え、設定画面がログインの状態を知る必要がある
- 5-A は作りが単純で、送るたびに本人が確認できる。押し忘れると、端末をなくしたときに古いバックアップしかない。5-B は押し忘れがない。全件を置き換える形（ADR 0049 の 2-A）のままで、上書きの守りを端末の ID と条件で作る必要がある。Issue 3 が 3〜5 時間ほど増える。5-C は 2 台でも使えるが、記録に更新日時と削除の印を持たせる変更が要り、MVP に入らない

同期の一般的なやり方（OS に任せる・丸ごとのバックアップ・記録ごとの同期・操作を混ぜる CRDT）と比べると、5-B は丸ごとのバックアップにあたる。トークの履歴のバックアップのように、1 台から自動で取り、戻すのは空の端末だけにする形。

## 選んだ理由

- 1 は B。MusicKit も計画に入れたい。ただし外部テスターに試してもらいたいのは「端末を超えて記録が残るか」なので、C1 ができたら MusicKit を待たずに配る
- 2 は A。App Store のビルドには、アカウントのコードが本当に入っていないのがいちばん単純で安全。テスターに配るものは Beta、App Store に出すものは Release、と分けて考えられる
- 3 は A。外部の人に配る以上、アカウントは Apple の側も含めてきれいに消せるべき。持たない情報は漏れないので、Apple のトークンは DB に置かない。増える時間は受け入れる
- 4 は A。どちらのビルドでも、書いてあることがうそにならない。Beta の文は状態ではなく決まりを書くので、オンにする前でも後でも正しく読める。憲法 II もこの形に改めた（1.5.0）
- 5 は B。毎回ボタンを押させるのは使う人に負担で、押し忘れればバックアップの意味がない。時間がかかっても自動にする。2 台の同期は C2 で、記録ごとの同期として作る

## 決めたこと

- 外部テスターに配る前に済ませる：レート制限と、`/health` を DB を見るものと見ないものに分ける（ADR 0051）。プライバシーポリシーを、Beta ではバックアップをオンにした人の記録を送る形に直す。外部テストの審査（Beta App Review）に要るものを確かめる。Beta のビルドを App Store の審査に出さない決まりを、App Store に出す手順に書く。テスターに、staging のデータは消すことがあり、正は端末だと伝える
- アカウントの削除と Apple のトークンの取り消しは Issue 2 で作る
- 自動で送ってよい条件（取り込むかを決め終わっている・端末に記録がある・サーバーのバックアップがないか、この端末から送ったもの）と、端末の ID の持ち方と、オン・オフの切り替え方（サインインでオンにするか、別の切り替えを置くか）は、Issue 3 の ADR で決める

## 見直す条件

- 11 月末に C1 が間に合わないとき（配る日か範囲を決め直す）
- Beta のビルドを App Store の審査に出してしまったとき、または出しそうになったとき（2 の決まりを仕組みにする）
- テスターから、2 台で使いたい・止まって聞かれるのが多い、と言われたとき（C2 を前倒しする）
- App Store にアカウントとバックアップを出す準備を始めるとき（2・4 を見直す）
