# 0006. 保存の冪等性を UI 層とデータ層の両方で守る

- 2026-07-28 ／ 承認
- 背景：カラオケボックス（地下など）の不安定な通信を前提に、保存ボタンの連打や再試行で同じ記録が二重に保存されないようにする

## 比較した案
- A. UI 層だけで防ぐ（保存中はボタンを押せなくする）
- B. データ層だけで防ぐ（同じ ID なら保存しない）
- C. 両方で防ぐ

## トレードオフ
- A は、タップしてからボタンが押せなくなるまでの間に 2 回目のタップが入ると防げない
- B は確実だが、保存中かどうかが画面から分からない
- C は二重に実装する手間がある

## 選んだ理由
- C。UI 層：保存ボタンをすぐ押せなくし、ProgressView と操作のブロックを出す（`isSaving`）。データ層：クライアントで作った UUID を冪等キーにし、`exists(uuid:)` で既にあれば insert と `singCount` の加算をせずに成功扱いにする
- 保存に失敗して再試行するときは同じ UUID を使う。編集は別の入口（`updateRecordingSession`）にして、冪等の判定で編集内容が無視されないようにしている

## 見直す条件
- サーバー同期を入れて、冪等性をサーバー側で保証するようになったとき
