# 0058. バックアップは本人がオンにしたときだけ、裏に回ったときに版の番号つきで送り、オフにしたら消す

- 2026-11-13 ／ 承認
- 背景：ADR 0053 の 5-B で、バックアップはオンにした後はアプリを閉じたときに自動で全件を送ると決めた。自動で送ってよい条件・上書きの守り・オン・オフの切り替え方は、Issue 3 の ADR で決めることにしていた。あわせて、同意の取り方・オフにしたときのサーバーの控え・端末に持つ状態の置き場所を決める

Apple の文書と個人情報保護委員会のガイドラインで確かめたこと：

- 「集める（collect）」は、端末の外に送り、リクエストの処理に要る時間より長く読める形で残すこと。自分のサーバーも含む。オンにした後に自動で送る形は、申告を省ける条件（まれ・主な機能でない・毎回本人が選ぶ）を満たさない（App privacy details）
- TestFlight のビルドも審査ガイドラインに従う（2.2）
- 審査ガイドライン 5.1.1 は、集める前に同意を取ること、同意を簡単に取り消せること、ポリシーをアプリの中からも開けること、保存期間と消し方を書くことを求める。5.1.x は要約でしか読めておらず、原文では確かめていない
- アプリ自身が集めるものも、Privacy Manifest の `NSPrivacyCollectedDataTypes` に書く。`UserDefaults` を使うなら、理由 `CA92.1` を書かないとアップロードを受け付けない
- `UserDefaults` は「機微でない、アプリの設定」を置く場所で、個人の情報や機微な情報は置かない。暗号化しない形でディスクに置き、端末のバックアップに含まれる
- 画面から直接受け取る個人情報は、あらかじめ利用目的を示す（個人情報保護法 21 条 2 項、通則編 3-3-4）。受け取ること自体に同意は要らない。使う必要がなくなったら、求めに応じて消す（35 条、通則編 3-8-5）
- `beginBackgroundTask` は、使える時間を約束しない。`endBackgroundTask` と必ず対にする。バックグラウンドの `URLSession` はファイルからしか送れず、アプリスイッチャーで終了すると取り消される

Mac で試したこと：アプリと同じ `ModelContainer(for:)` で、Beta 相当（記録＋状態のモデル）で保存した保存先を Release 相当（記録だけ）で開くと、開けた。記録は残り、状態のモデルの表は消えた。iOS の実機では確かめていない。

## 比較した案

1. オン・オフ
- A. サインインしたらオンにする
- B. サインインとは別に、バックアップの切り替えを置く（初めはオフ）

2. 同意の取り方
- A. 設定の説明の文だけで知らせる
- B. オンにする前に、送るもの・送らないもの・目的・置き場所・止め方を 1 枚で見せ、「オンにする」を押したら同意とする

3. オフにしたとき
- A. 送るのをやめるだけで、サーバーの控えはアカウントを消すまで残す
- B. 送るのをやめ、サーバーの控えも消す（件数を見せて確認する）

4. ほかの端末のバックアップを上書きしない守り（FR-4）
- A. 端末ごとの ID を作り、送った端末を `backups` に記録して比べる
- B. サーバーの控えに版の番号を持たせ、最後に送った版と一致するときだけ置き換える（`If-Match`。ないときは `If-None-Match: *`。違えば 412）

5. 送るタイミング
- A. 裏に回ったとき（`scenePhase` が `.background`）に `beginBackgroundTask` で送り、送れなかったら次に前に戻ったときに送る。「今すぐバックアップ」のボタンも置く
- B. バックグラウンドの `URLSession` に預ける
- C. `BGTaskScheduler` に、後で起こしてもらう
- D. 記録を保存した直後に送る

6. 端末に持つ状態の置き場所
- A. `UserDefaults`
- B. SwiftData に状態のモデルを足す
- C. Keychain
- D. 自分でファイルに書く

## トレードオフ

- 1-A は操作が少ないが、サインインと送ることの同意が分けられず、オフにする手段も別に要る。1-B は操作が 1 つ増えるが、サインインだけして送らない状態を作れる
- 2-A は作りが単純だが、送る前に目的を示したと言いにくい。2-B は 1 枚増えるが、何が端末の外に出るかを、送る前に本人が読める
- 3-A は、オフを一時的に使ってもすぐ戻せる。代わりに、使わない控えを持ち続け、ポリシーにも「オフにしても残る」と書くことになる。3-B は同意を取り消したらもう持たない。端末が正なので消えても困らないが、オフにした直後に端末をなくすと戻せない
- 4-A は「どの端末が送ったか」が分かるが、端末の ID はプライバシーのラベルの Device ID に当たるおそれがあり、置き場所と、端末を移したときの扱いも決める必要がある。4-B は HTTP の決まった形（条件つきのリクエスト）で、ID を持たずに済む。何度送っても、遅れて送っても結果が正しく、正しさが送るタイミングに左右されない
- 5-A は作りが軽く、ホーム画面に戻すだけで試せる。圏外で閉じると、次に開くまで送らない。5-B は電波が戻れば iOS が送るが、ファイルに書き出す・後から届く結果を受ける作りが要り、412 の確認を出す場面がない。アプリスイッチャーで終了すると取り消される。5-C はいつ動くかを iOS が決め、何時間も後になることも、動かないこともある。5-D は控えがいちばん新しいが、全件を置き換える形（ADR 0049 の 2-A）では 1 曲ごとに全件を送ることになる
- 6-A は Apple の言う用途（機微でない設定）に合い、足すものが少ない。代わりに、manifest に `CA92.1` を書く。6-B は申告が要らず、Repository の形もそろうが、モデルと Repository が増える。機能のない Release で開くたびに状態の表が消え、Core Data のエラーのログが出る。6-C は秘密のための場所で、アプリを消しても残るので、入れ直したときに同意を取り直さないまま始まる。6-D は申告が要らないが、読み書きと壊れない工夫を自分で作る
- 守りの強さは 6-A と 6-B で同じ。どちらもアプリの領域にあり、iOS のファイルの守り（既定は最初のロック解除の後に読める）がかかる。メモ付きの記録も SwiftData にあるので、状態を SwiftData に置いても守りは固くならない

## 選んだ理由

- 1 は B。サインインとバックアップの同意を分け、送るかどうかを本人がいつでも決められるようにする
- 2 は B。送る前に、何が端末の外に出て何が出ないかを、本人が読めるようにする。Apple の同意の求めと、利用目的を先に示す法の求めを 1 枚で満たす
- 3 は B。同意を取り消したら、もう持たない。持たない情報は漏れない（ADR 0049）。端末が正なので、消しても記録は失わない
- 4 は B。正しさを、送るタイミングや端末の値に頼らずサーバーで守る。端末の ID を持たずに済む
- 5 は A。長く運用できるかは、どの仕組みで送るかより、いつ送っても壊れない作りかで決まる。4-B でそれを守ったうえで、いちばん軽く試しやすい A にする。送る処理ときっかけを分けておき、B や D は後から足せるようにする。記録が多くなったときの工夫は、ここでは決めずに切り離す
- 6 は A。置くものを、読まれても書き換えられても害のないものに絞る。守りの強さは SwiftData と同じで、足すものがいちばん少ない

## 決めたこと

- 同意の画面には、送るもの（曲名・気分・点数・歌った日時・もう一度歌いたいか・歌い切ったか・記録した画面）、送らないもの（メモ）、目的（端末をなくしたとき・機種を変えたときに戻すため）、置き場所（自前のサーバー。東京の Cloud Run と、シンガポールの Neon）、オンにした後は自動で送ること、止め方、staging のデータは消すことがあること、プライバシーポリシーへのリンクを書く
- 同意には版を持たせる（今は 1）。送る項目を増やすときは版を上げ、オンのままでも同意を取り直すまで送らない
- `backups` に版の番号（置き換えるたびにサーバーが 1 増やす整数）を持たせる。`PUT /v1/backup` は、`If-Match: "<版>"` か、控えがないと思っているときの `If-None-Match: *` を必ず付ける。条件がなければ 428、合わなければ 412 を返し、どちらも置き換えない。成功したら新しい版と日時を返す。`GET /v1/backup/summary` も版を返す
- ほかの端末の控えと食い違ったとき（412）は、自動では送らない。設定のバックアップの欄に「サーバーの N 件を、この端末の M 件で置き換えます」を出し、本人が選んだら、そのとき読んだ版を `If-Match` に付けて送る
- 端末に記録が 1 件もないときは送らない（FR-5）。取り込み（Issue 4）では、取り込んだ控えの版を覚え、その後の自動の送信が 412 にならないようにする
- 送る処理（中身を作る・前回と比べる・条件つきで送る）と、きっかけ（裏に回ったとき・前に戻ったとき・ボタン）を分ける。同時に 2 つは送らない。前回送った中身のハッシュはメモリにだけ持ち、同じなら送らない
- 裏に回ったときは、すぐに `beginBackgroundTask` を始め、終わったら・時間切れのときに `endBackgroundTask` を呼ぶ。前に戻ったときは、前回失敗していれば送る
- 自動のときの失敗は画面に出さない。設定に「最後のバックアップ」の日時と、最後の失敗の理由（届かない・サーバーの失敗・サインインし直す・確認が要る・大きすぎる）を出す。「今すぐバックアップ」は失敗をその場に出し、やり直せる。401 は今のサインアウトと同じく端末のトークンを消す
- オフにするときは、サーバーの件数を見せて確認し、`DELETE /v1/backup`（控えがなくても 204）を呼ぶ。消せなくても端末ではすぐオフにし、設定に「サーバーのバックアップを消せませんでした」と「もう一度消す」を出す
- `UserDefaults` に置くのは、オン・オフ、同意した版、最後に送った版の番号、最後に成功した日時、最後の失敗の理由の 5 つだけ。トークンは Keychain、記録は SwiftData のまま。サインアウトとアカウントの削除で 5 つとも消す。サインアウトではサーバーの控えは残し、アカウントの削除では `backups` も一緒に消える（`ON DELETE CASCADE`）。削除の確認の文に、バックアップも消えることを足す
- Privacy Manifest はビルドで分ける。Beta のものには、集めるものと `NSPrivacyAccessedAPICategoryUserDefaults`（理由 `CA92.1`）を書く。Release のものは今のまま（集めるものも、理由の要る API もない）。App Store のプライバシーのラベルは、Release に機能がないので「収集なし」のまま
- プライバシーポリシーは、外部テスターに配る前（Issue 5）に、App Store 版と TestFlight 版に書き分ける。法 32 条の事項（利用目的・開示等の手続・安全管理措置とサーバーの国の名前・苦情の申出先）を書き、氏名と住所は「お問い合わせいただければ遅滞なくお答えします」とする

## 見直す条件

- テスターの控えが古いまま残っていると、サーバーの更新日時で分かったとき（5 に B を足す）
- 記録が数千件になり、全件を送るのが重くなったとき、または 2 台で使いたいと言われたとき（変わった分を送る同期 C2 を設計し、5 に D を足す）
- 送る項目を増やすとき（同意の版を上げる）
- App Store にバックアップを出す準備を始めるとき（ラベル・ポリシー・manifest を Release に合わせる）
- iOS の実機で、`UserDefaults` か SwiftData の扱いがこの ADR の前提と違うと分かったとき（6）
