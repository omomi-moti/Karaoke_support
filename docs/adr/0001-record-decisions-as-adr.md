# 0001. 技術判断を ADR として 1 件 1 ファイルで残す

- 2026-10-14 ／ 承認
- 背景：判断の理由を「技術的な工夫」として 1 つの文章（`technical_decisions.md`）にまとめていたため、判断が変わると上書きするしかなく、何から何に変えたかの経緯が残らなかった

## 比較した案
- A. 今までどおり「工夫と解決策」の文章を更新していく
- B. `docs/adr/` に 1 件 1 ファイルで ADR を置く
- C. 1 つのファイルに ADR を番号順に足していく

## トレードオフ
- A は書くのが楽だが、変更の経緯が消える
- B はファイルが増えるが、新しい判断は新しいファイルを足すだけで済み、複数のブランチで同時に足してもぶつかりにくい
- C は全体を上から読めるが、長くなり、複数のブランチで同時に足すと一覧とファイル末尾が毎回ぶつかる

## 選んだ理由
- B。最初は C で書き始めたが、1 件が 20〜30 行あり、11 件で約 300 行になった。また、docs のブランチと機能のブランチで同時に ADR を足す状況がすぐに起き、1 ファイルだと毎回コンフリクトする
- 一般的な ADR より軽くし、書く項目と運用のルールは [README](README.md) にまとめる
- 0002〜0009 は、以前 `technical_decisions.md` の「技術的な工夫と解決策」に書いていた内容を移したもの。日付は元の文章をそのファイルに書いた日
- 0010 は、同じファイルの「仕様書群の矛盾管理」を背景に、2026-10-14 に判断し直したもの

## 見直す条件
- 件数が増えて一覧から探しにくくなったら、README の一覧に分類の列を足す
