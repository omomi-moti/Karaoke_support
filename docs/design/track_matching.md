# 曲名の一致・検索の方針

**対象:** 記録シートの曲名サジェスト（もしかして）、今後の表記ゆれ対応（#94〜#96）、MusicKit 連携。

**参照実装:** `TrackSuggestionRanker` / `TrackMatchTier`（`Sources/Domain/Helpers/`）、`RecordingSheetViewModel.updateTrackSuggestions(for:)`。

---

## 一致の種類と使い分け

| 方法 | 内容 | 向いている場面 | このアプリでの使い道 |
|------|------|----------------|----------------------|
| **完全一致** | 文字列がまったく同じ | 同じものかどうかの判定 | `TrackRepository.getOrCreate` で同じ曲か決める（#94 以降は正規化した値での完全一致） |
| **前方一致** | 先頭から一致する | 入力途中の補完 | サジェストの 1 段目 |
| **単語の先頭一致** | 途中の単語の頭で一致する（「live」→「Lemon (Live)」） | 複数の単語でできた名前の補完 | サジェストの 2 段目 |
| **部分一致** | どこかに含まれる | 「探す」画面での検索 | サジェストの 3 段目・検索タブ（`searchLocal`） |
| **読み・かなの統一** | ひらがな/カタカナ、漢字の読みをそろえてから比べる | 日本語の表記ゆれ | 未実装（#95）。比べる前の下ごしらえ |
| **あいまい一致（編集距離など）** | 1〜2 文字違っても当てる | 打ち間違い | 未実装（#96）。他で 1 件も当たらないときの保険 |
| **全文検索インデックス** | 大量の文章を高速に検索する | 数万件以上のデータ | 使わない。端末内の曲は多くても数百件で、SwiftData にもこの機能はない |

## 原則: 判定と並べ方を混ぜない

- **同じ曲かどうかの判定**（`getOrCreate`）は **完全一致のみ**。間違えると別の曲の記録や歌唱回数がまとめられ、元に戻すのが難しいため。
- **候補の並べ方**（サジェスト）は、前方一致などを使ってユーザーが選びやすい順にする。最終的に曲を決めるのはユーザーのタップ。
- あいまい一致・読みでの一致は **候補を出すためだけ** に使い、同じ曲の判定には使わない。

## 記録シートのサジェスト（もしかして）

### 流れ

1. `.task(id: manualName)` から `updateTrackSuggestions(for:)` を呼ぶ（入力が止まってから 300ms 後に検索）
2. **絞り込み**: `searchLocal`（`userEnteredName` の部分一致。DB 側の `localizedStandardContains`）
3. 入力が既存の曲名と完全一致なら何も出さずに終わる（下記「その他の決めごと」）
4. 歌唱回数 0 の曲と、Spotify ID を持つ曲を除く
5. **並べ替え**: `TrackSuggestionRanker.rank`
6. 先頭 5 件を表示する

**5 件に絞る前に並べ替える。** `searchLocal` は歌唱回数の多い順に返すため、先に絞ると、前方一致の曲が 6 件目以降にあった場合に切り捨てられる。

### 並べ方

2 曲を比べるとき、上から順に見て、違いが見つかった時点で決める。

| 順 | 条件 | 並び | 理由 |
|----|------|------|------|
| 1 | 一致の段 | 前方一致 > 単語の先頭一致 > 部分一致 | 今打っている文字に合っているかが最優先。「a」と打った人は a で始まる曲を探していることが多い。段の中では、曲名の先頭で始まる前方一致、途中の単語が打った文字で始まる単語の先頭一致（「live」→「Lemon (Live)」）、単語の頭ですらなく含んでいるだけの部分一致、の順に意図に近い |
| 2 | 歌唱回数 | 多い順 | 同じ段なら、よく歌う曲ほどまた歌う可能性が高い |
| 3 | `updatedAt` | 新しい順 | 回数も同じなら、最近触った曲を上にする（下記の注意を参照） |
| 4 | 曲名 | 辞書順 | 毎回同じ並びにするための保険。`sorted` は条件が同じ要素の並びを保証しない |

### 段の判定（`TrackSuggestionRanker.tier(of:for:)`）

良い段から順に確認し、当てはまった時点で決める。

1. `range(of:options:)` に `.anchored` を付けて **先頭から一致するか** → 前方一致
2. 一致した位置の **直前の文字が空白・記号** か → 単語の先頭一致。1 回目の一致が単語の途中でも、後ろの一致を続けて確認する（「an」→「Banana Anthem」は Anthem で単語の先頭一致）
3. どちらでもない → 部分一致

**比べ方のルール:** 大文字小文字・濁点など・全角半角を区別しない（`.caseInsensitive` / `.diacriticInsensitive` / `.widthInsensitive`）。DB 側の `localizedStandardContains` とそろえるため。ここがずれると、DB で見つかった曲が並べ替えで不当に下の段に入る。

**単語の区切り:** 「直前が空白・記号」だけで判定する。`enumerateSubstrings(.byWords)` は日本語を形態素で区切り（「打上花火」→「打上」「花火」）、区切り位置が予想しづらいため使わない。空白のない日本語の曲名は、ほぼ「前方一致」か「部分一致」になる。

### その他の決めごと

- **1 文字目から出す。** 1 文字でも段分けで前方一致が上に来るので、部分一致を除外しない。
- **入力が既存の曲名と完全一致なら何も出さない。** そのまま保存すれば `getOrCreate` で既存の曲につながるため。判定は `getOrCreate` と同じ条件（Spotify ID なし・曲名が完全一致）で、候補から除く歌唱回数 0 の曲も含める。
- **歌唱回数 0 の曲は候補に出さない。** 記録を全部消した曲（打ち間違いで作った曲など）は Track だけ残るため。
- **Spotify ID を持つ曲は候補に出さない。** 候補を押すと曲名だけが入力欄に入り、保存時の `getOrCreate(spotifyTrackId: nil, userEnteredName:)` は Spotify ID を持たない Track しか探さないため、既存の曲につながらず別の Track が作られてしまう。
- **一致する曲がなければ「候補はありません」を出す。** 検索に失敗したときは出さない（候補があるのに無いと誤解させないため）。
- 候補を押すと入力欄の文字が置き換わる（曲を固定表示にするモード切り替えはしない）。

### 既知の制約

- **`updatedAt` は「最後に歌った日時」の近似。** 記録の保存だけでなく、編集・削除でも更新される。また歌唱日時を過去にして保存しても、保存した時刻になる。正確に出すには曲ごとに記録（`sessions`）を読み込む必要があり、回数も同じときの決め手にすぎないためコストが見合わないと判断した。
- **候補を選ばずに打ち切ると、別の曲として保存される。** 「lemon」と「Lemon」は `getOrCreate` の完全一致では別の曲になる。#94（正規化）で対応する。
