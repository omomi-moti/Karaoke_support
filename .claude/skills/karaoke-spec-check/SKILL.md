# 決まりを満たしているかの確認

変更が、文書に書いた決まりを**層ごとに**満たしているかを確かめる。
気になる箇所を思いつきで追うのではなく、先に条件を全部書き出し、1 つずつ確かめる。
思いつきで追うと、文書に書いてある道だけを見て、コードにある別の道（たとえば状態を消す道の 1 つ）を見落とすため。

## ほかのスキルとの分け方

| スキル | 受け持ち |
|---|---|
| `karaoke-spec-check`（これ） | 文書の決まりを満たしているか。層ごとの表で出す |
| `karaoke-review` | 壊れても気づきにくい 13 点。実害を 1 文で言える指摘だけを出す |
| 標準の `code-review`・`security-review`・`simplify` | 一般的な不具合・セキュリティ・書き方の整理 |

PR の前は、このスキルを先に、`karaoke-review` を後に流す。
`karaoke-review` の 13 点に当たる条件（メモがサーバーに渡らない、など）は、表に「karaoke-review で見る」とだけ書き、ここでは確かめない。同じ指摘が 2 回出ないようにするため。

途中の操作の扱いは、次のように分ける。

- ViewModel が `await` の後に、古い結果で画面の状態を書き換える → `karaoke-review`（古い非同期結果の上書き）
- 文書が「いつも」成り立つと決めたこと（同時に送らない、自動では上書きしない、オフにしたら送らない、など）が、途中の操作（オフ・サインアウト・同じ操作がもう一度）で破れる → このスキル（手順 3 の 3）

## 手順

### 1. 対象と範囲を決める

```bash
# ブランチ全体
git diff main...HEAD --stat
git log main..HEAD --format='%h %s%n%b' | grep -E 'Refs #|Closes #'
# 1 つのコミットだけ（A はその親）
git diff A B --stat
```

- 対象の差分（ブランチ全体・1 つのコミット・未コミット）と、Issue の番号を決める。分からなければ聞く。
- PR の途中の手順だけを見るときは、その手順の範囲を決める。範囲の外の条件は消さずに「手順 N で確かめる」と残す。

### 2. 決まりを集める

決まりはスキルに書き写さず、毎回元の文書から読む。書き写すと、元を直したときに食い違うため。

| 元 | 条件にするもの |
|---|---|
| `gh issue view N` | 受け入れ条件のチェックボックスを 1 つずつ |
| Issue と差分が指す ADR | 「決めたこと」。「トレードオフ」「選んだ理由」は条件にしない |
| `docs/backend_design.md` | サーバー・アカウント・バックアップに触れるとき。FR・NFR・データの流れ・責任の分け方 |
| `docs/constitution.md` | いつも |
| 触った層の `.claude/rules/*.md` と CLAUDE.md の「どこでも効く決まり」「DI の配線」 | いつも |
| CLAUDE.md の「文書の更新を確かめる」と、各ルールの末尾の「見直す文書」 | 文書の層の条件 |

### 3. 層ごとに条件を書き出す

層：Domain／Data／Presentation（View・ViewModel）／App（DI・起動）／サーバーの handler・service・store・migrations／テスト／文書。触っていない層は書かない。

書き方：

- 1 つの条件は 1 文で、確かめられる形にする（「〜のときは〜しない」「〜を持たない」）。
- 元を 1 つ付ける（例：`#161 受け入れ条件 iOS 7 つ目`、`ADR 0058 決めたこと 9 つ目`、`憲法 II`）。元のない条件は作らない。下の「必ず足す 4 つ」から作った条件は、関係する決まりと並べて `スキル 3-N` を元にしてよい（例：`ADR 0058 決めたこと 10（スキル 3-1）`）。
- 層をまたぐ条件（同じものを共有する、など）は、それを守っている層に置く。

抜けやすいので、次の 4 つは必ず足す：

1. **状態の前提が変わる道を全部挙げる。** 端末に置く状態ごとに「誰の・何の前提で正しいか」（例：今サインインしているアカウントの状態）を書き、その前提が変わる箇所（例：トークンを保存する・消す箇所）を `grep` で全部拾う。拾った箇所ごとに、状態をどう扱うかを条件にする。文書に書いてある道だけを条件にすると、書いていない道で状態が残る。アプリの外で前提が変わる道（入れ直し・機種変更での移行・ほかの端末）も足す。
2. **置いた状態が消える条件を対にする。** 「失敗を置く」なら「直ったら消える」も条件にする。「直った」には、成功したときだけでなく、処理を省く道（同じ中身なので送らない、など）で結果が正しくなったときも入れる。消えないと、古い表示が残り続ける。
3. **「いつも」成り立つ決まりは、途中でほかの操作が入っても成り立つかを条件にする。** 「同時に送らない」「自動では上書きしない」などは、途中でオフ・サインアウト・同じ操作がもう一度、の場合も書く。
4. **テストの層には、条件ごとにどのテストが守っているかと、テストが待つ時間に頼っていないか（並べて流しても結果が変わらないか）を書く。** 決まった時間だけ待って順番を作るテストは、並べて流すと順番が入れ替わって落ちる。

### 4. 条件ごとに確かめる

確かめ方は強い順に 5 つ。表にどれで確かめたかを書く。

| 確かめ方 | 中身 |
|---|---|
| テスト | 今あるテストがこの条件を確かめている。テストの名前を書く |
| 試し | 一時的なテストを書いて流した。流したらテストを消し、ファイルを元に戻す（下の「試しのやり方」） |
| 読んだ | コードを読んで確かめた。`file:line` を書く。分岐の両側と、呼び出し先まで読む |
| 未確認 | 確かめられなかった。理由を書く（実機が要る、など） |
| 対象外 | この範囲の外（「手順 N で確かめる」）か、「karaoke-review で見る」 |

結果の記号は次のとおりに付ける。確かめていない推測を不具合として出さない（CLAUDE.md）。

| 記号 | 付けるとき |
|---|---|
| ✅ | 満たしていると確かめた |
| ❌ | 満たしていないと確定した。試しで落ちた、または読んだだけで違反が確定する（名前の決まりなど） |
| ⚠️ | 満たしていない道はコードで確かめたが、実際に起きるかが環境しだい（実機・機種変更の移行など）で確かめられない。または、条件そのものを確かめられなかった |
| — | 対象外（後の手順・karaoke-review） |

❌ と ⚠️ は、どちらも「満たしていない条件」の節に入れる。

コードと文書が食い違っていて、コードの側がわざとそうしている（テストでその動きを固定している、など）ときは、どちらが正しいかをこのスキルでは決めない。❌ にして、修正案に「コードを文書に合わせる」「文書をコードに合わせる（承認した ADR は書き換えず、`docs/` を直すか ADR を足す）」の 2 つを並べ、本人が決めると書く。

#### 試しのやり方

1. 変えるファイルを `cp` でスクラッチパッドに控える。git の stash・reset・checkout は使わない（ほかのセッションと同じフォルダを使っていることがある）
2. 一時的なテストを足して流す。`-resultBundlePath` は、スクラッチパッドの下に置く（リポジトリの中に置かない）
3. 控えからファイルを戻し、`git status --short` が試しの前と同じことを確かめる。報告にもそう書く

### 5. 報告する

```
## 層ごとの表

### {層}
| 条件 | 元 | 結果 | 確かめ方 |
|---|---|---|---|
| … | ADR 0058 決めたこと 5 | ✅ | テスト：`unchanged` |
| … | #161 iOS 7 | ❌ | 試し |
| … | 憲法 II | — | karaoke-review で見る |

## 満たしていない条件
### {一行の要約}
**条件**: … **元**: … **該当**: file:line
**症状**: 利用者の画面やデータで何が起きるか。1 文
**確かめたこと／確かめていないこと**: …
**修正案**: 最小の差分

## 後の手順で確かめる条件
- …（手順 N）
```

結果の記号は手順 4 の表のとおり。
満たしていない条件がなければ「ゼロ」と書く。条件が多くても、表は省かない。何を確かめ、何を確かめていないかが、表で分かるようにするため。

## このスキルが見ないこと

- `karaoke-review` の 13 点。表には「karaoke-review で見る」とだけ書く
- 一般的な不具合・書き方・性能・アクセシビリティ（標準のレビューの受け持ち）
- 決まりそのものの良し悪し。決まりを変えるかは本人が決め、変えるなら ADR を足す
- 文書にない「こうしたほうがよい」という提案。浮かんだら、表とは分けて「参考」として最後に短く書く
