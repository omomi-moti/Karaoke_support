# Karaoke_support コードレビュー

このプロジェクトで**壊れても気づきにくい**点だけを見る。iOS のアプリで 6 点、サーバーで 5 点。

「気づきにくい」が選定基準になっている。コンパイラが弾くもの、テストが落ちるもの、
一般的な Swift の作法は含めていない。それらは他の手段で既に守られているため、
ここで重ねて指摘してもノイズが増えるだけになる。

## ワークフロー

### 1. 対象を確定する

```bash
git diff main...HEAD --stat
```

未コミットの変更が対象なら `git diff` / `git diff --staged` を使う。
どちらを見ればいいか曖昧なら、確定させてから進める。

### 1.5. `server/` に変更があれば、先に機械で見られるものを流す

`server/` の中で打つ。

```bash
gofmt -l .
go vet ./...
go test ./...
go run golang.org/x/vuln/cmd/govulncheck@v1.9.0 ./...
```

`gofmt -l` が何かを出す、`vet` か `test` が落ちる、`govulncheck` が脆弱性を出す、のどれかなら、
ルールの指摘とは分けて「機械のチェック」として出力をそのまま報告する。

### 2. 触った領域から、読むルールを絞る

`references/rules.md` は全部読まなくていい。変更内容に応じて必要な節だけ読む。

| 変更に含まれるもの | 読む節 |
|---|---|
| `save` / `update` / `delete` / Repository 呼び出し | 編集の握り潰し、二重保存、Repository を経由しない DB 書き込み |
| `await` / `Task` / `.task` / ViewModel の状態更新 | 古い非同期結果の上書き |
| `@Model` へのプロパティ追加、`UserDefaults`、API 応答の保存 | Spotify メタデータの永続化 |
| 新規の View / ViewModel / Repository | Presentation への具体 Repository 型の漏れ |
| `server/` の SQL・store・handler | 他人の記録に届く SQL、ログやエラーの返事に記録の中身や秘密が出る |
| `server/` のリクエストの型、iOS の `BackupSnapshot` | メモがサーバーに渡る |
| `server/migrations/` | 流し済みのマイグレーションの書き換え |
| URL・鍵・パスワードらしい文字列、設定ファイル | 秘密がリポジトリに入る |

### 3. 変更行だけでなく、囲むシンボル全体を読む

diff の hunk だけで判定しない。メソッド全体、できれば型全体を読む。

このプロジェクトの事故は「呼び出し先の分岐」で起きる。
たとえば `save()` の1行だけ見ても、その id が新規か既存かは分からない。
分岐と、その分岐に入る条件を追わないと判定できない。

### 4. 指摘を裏付ける

報告する前に `file:line` を特定し、**実際にその行を読む**。
grep のヒットは根拠にならない。

そのうえで、rules.md の各節にある「誤検知しやすいケース」を必ず確認する。
このプロジェクトには、ルールの grep に引っかかるが**正しい**コードが実在する。
特に保存フローの id 使い回しは、正しい実装なのに毎回ヒットする。

### 5. 実害を1文で言えるものだけ報告する

報告の前に自問する:

> このまま出荷したら、ユーザーの画面で（サーバーなら、利用者のデータやログに）何が起きるか？

具体的な症状として1文で書けないなら、報告しない。
「規約違反です」「一貫性がありません」だけの指摘は出さない。

これは厳しすぎる基準に見えるかもしれないが、理由がある。
的外れな指摘が混ざると、その中に紛れた本物の指摘も一緒に読み飛ばされる。
指摘の数ではなく、指摘の信頼度がこのスキルの価値になる。

## 報告フォーマット

```
### [ルール名] 一行要約
**該当**: Sources/Presentation/.../Foo.swift:42
**症状**: ユーザーの画面で（サーバーなら、利用者のデータやログに）何が起きるか。1文
**根拠**: なぜそうなるか。2〜3文
**修正案**: 最小の差分。可能ならコード
```

秘密が入っている指摘では、値そのものを報告に書き写さない。`file:line` と種類（「Neon の URL」など）だけを書く。

重大度順に並べる。目安は以下だが、実際の影響で判断してよい。

1. 他人の記録に届く SQL（ほかの利用者の記録が見える・消える）
2. 秘密がリポジトリに入る（公開リポジトリなので、コミットした時点で漏れる）
3. Spotify メタデータの永続化・メモがサーバーに渡る（憲法の違反。コードの問題では済まない）
4. 編集の握り潰し（無言で失敗する）
5. 流し済みのマイグレーションの書き換え（staging だけで落ちる）
6. 古い非同期結果の上書き（再現しにくい表示崩れ）
7. ログやエラーの返事に記録の中身やトークンが出る
8. 二重保存
9. Repository を経由しない DB 書き込み
10. Presentation への具体 Repository 型の漏れ

**指摘がゼロなら「ゼロ」と明記する。** 無理に絞り出さない。
どのルールにも当たらない改善提案が浮かんだ場合は、指摘とは分けて「参考」として最後に短く添える。

## このスキルが見ないこと

以下は見つけても黙っておく。守備範囲外だと分かったうえで外している。

- **一般的な SwiftUI の作法、非推奨 API、アクセシビリティ、パフォーマンス**
  汎用スキル（swiftui-pro 等）の担当。併用したときに重複指摘になる
- **命名規則、`#Preview` の有無、色リテラル**
  実害を1文で言えないため意図的に外した。特に `Color.white.opacity(0.2)` のような
  半透明オーバーレイはこのプロジェクトの定型句であり、指摘すると誤検知だらけになる
- **`@MainActor` / `async throws` の付与漏れ**
  Repository は Protocol 側に `@MainActor` が付いており、コンパイラが強制済み
- **一般的な Go の作法、書式、エラーの包み方**
  gofmt・`go vet` と汎用のレビューの担当。手順 1.5 で流した結果だけを報告する

## 前提として知っておくこと

このプロジェクトの Repository パターンは、**Apple の SwiftData 標準スタイル
（View で `@Query` + `modelContext.insert`）にあえて逆らう意図的な選択**である。
根拠はテスタビリティ（ViewModel のユニットテストの多くが、モック Repository を注入して書かれている）。

したがって「Apple 標準に寄せるべきでは」という提案は、それ自体は正当な設計議論であり、
このスキルはそれを却下する根拠にはならない。
「Repository を経由しない DB 書き込み」は、現在の設計を選び続ける限り一貫させるためのルールであって、
設計判断そのものを固定するものではない。

同じ理由で、各ルールは**不変条件**として書いてある。実装手段は指定しない。
手段まで縛ると、正当なリファクタをこのスキルがブロックしてしまう。
